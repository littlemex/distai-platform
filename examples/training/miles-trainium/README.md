# GRPO-style post-training smoke test: SGLang-Neuron rollout on Trainium

This is a reference for one narrow question: can a GRPO-style post-training loop (generate, reward, train, update the policy's weights) close at least once when the rollout step runs through [`sgl-project/sglang-neuron`](https://github.com/sgl-project/sglang-neuron) -- the public preview SGLang platform plugin for AWS Trainium -- on one real `trn2.3xlarge` node? It is not `miles` (`radixark/miles`) itself, and it is not `miles`'s own training backend (Megatron-LM, `fsdp` or `torchtitan`); see "Relationship to miles" below for why. **Result: closed.** On a real `trn2.3xlarge` spot node, the loop ran 2 steps end to end -- generate, reward, CPU train, restart-based weight update, generate again -- in 1090.5 seconds total; step 0's mean reward was 16.0000 (loss -7.8760), step 1's was 13.8750 (loss -4.2082). Two real-hardware-only defects blocked earlier attempts and are fixed here: `sgl-project/sglang-neuron`'s device sampler defaults to a greedy-only mode that refuses any sampled request, and its restart path refuses a checkpoint whose declared dtype is not `bfloat16` (this script's CPU-training copy is `float32`). See "What actually ran" for the full attempt history (6 real-machine attempts across two sessions) and "On the two defects this found" for what each one is and how it was confirmed.

## Relationship to miles

`awslabs/awsome-distributed-ai`'s `examples/training/miles` already references `miles`, a fork of `slime`, for GRPO post-training on GPU (Megatron-LM + SGLang + Ray). `miles`'s own weight-transfer protocols are pluggable (`cuda_ipc`, `broadcast`/NCCL, `disk-delta`, `p2p`, `http_lora`, `ici` for TPU), but its rollout backend is SGLang only, with no abstraction for swapping the inference engine itself. `sglang-neuron`'s own documentation states its weight-update and LoRA endpoints are refused (see "What SGLang-Neuron is, and is not, documented to support" below), so `miles`'s existing rollout client cannot be pointed at it unmodified. This example does not attempt that swap; it is a standalone, minimal reference built specifically to answer the rollout-on-Trainium question on its own, written against `sglang-neuron`'s actual, documented API rather than through `miles`.

## What SGLang-Neuron is, and is not, documented to support

- `sgl-project/sglang-neuron` is an independent plugin (not part of core `sgl-project/sglang`), pinned to upstream SGLang commit `43881a7`, published by the AWS Neuron team through Amazon ECR Public. Current release: `v0.1.0`, image `public.ecr.aws/neuron/pytorch-inference-sglang-neuron:v0.1.0-neuron-py314-sdk-2.33.0-ubuntu26.04` (11.7 GB across 41 layers, by its own registry manifest).
- Its own docs state: *"This release is a public preview."*
- Its own model-recipe docs ([`docs/model-recipes/qwen3.md`](https://github.com/sgl-project/sglang-neuron/blob/4e2432622bfab2c6663d12286a6813ef1a40bfe6/docs/model-recipes/qwen3.md)) state LLM serving (Qwen3, GLM-4, DeepSeek-V2-Lite, GPT-OSS and others) "runs on Trn3 instances"; diffusion models (FLUX, Wan2.2 and others) target `trn2.48xlarge`. **Neither claim names `trn2.3xlarge`.** This example runs LLM serving on `trn2.3xlarge` anyway, off-label by the project's own documentation, because the validated flags for Qwen3-0.6B ask for exactly four NeuronCores (`--tp-size 4`) -- the same count `trn2.3xlarge`'s device plugin advertises (confirmed on real hardware by this investigation: `aws.amazon.com/neuron: "1"`, `aws.amazon.com/neuroncore: "4"` allocatable) -- not because the instance is a documented target.
- "What is refused" (close paraphrase of the same doc's own section): a non-bfloat16 dtype; a quantized checkpoint; sliding-window attention; attention biases; a scaled RoPE; attention/KV head counts that do not split or replicate evenly over the tensor-parallel ranks; `--ep-size` other than 1; a KV cache dtype other than `auto`/`bf16`; and, from the plugin's own LoRA/weight-update documentation, dynamic weight reload and LoRA adapters. **There is no live-reload API** (no equivalent of upstream SGLang's `/update_weights_from_disk`); the only officially-supported way to pick up new weights is to restart the server pointed at a new checkpoint directory.
- **The device sampler defaults to greedy-only.** `sglang_neuron/sampling.py`'s `sampler_mode()` reads `SGLANG_NEURON_SAMPLER`, defaulting to `"greedy"` when unset; `general_plugin.py`'s admission hook then refuses, at the first request, anything that is not `temperature` below `1e-6` or `top_k=1` (`sglang_neuron/sampling.py`'s `validate_device_sampling_request`). This is launch-time configuration, not a documented per-model limit, so it is easy to hit without the model-recipe docs mentioning it; see "What actually ran" below for how this PR found it on real hardware.
- **`--dtype` defaults to `auto`, which reads the checkpoint's own `config.json`.** `check_bf16_launch` (`sglang_neuron/models/transformer/config.py`) refuses a checkpoint whose resolved dtype is not `bfloat16` -- which includes a checkpoint `transformers.save_pretrained()` wrote while training ran in `float32`, even though the graphs' bfloat16 requirement itself was already documented (see "What is refused" above). Passing `--dtype bfloat16` explicitly on every launch bypasses the `auto` resolution regardless of what the checkpoint declares.

## Design

| Part | Where it runs | Why |
|---|---|---|
| Rollout (generation) | `sgl-project/sglang-neuron`, `--tp-size 4`, all four NeuronCores of one `trn2.3xlarge` | The actual rollout engine this reference is testing, through its own OpenAI-compatible `/v1/completions` route |
| Reward | Plain Python (CPU, in the same Pod) | A free, deterministic rule (count of alphabetic words); the number itself is not the point, only that it varies across samples so GRPO's group-relative advantage has something to normalize |
| Training (loss, backward, optimizer step) | Plain CPU `transformers` (eager, variable-length batches), same Pod | `sglang-neuron`'s own `--tp-size 4` already claims every NeuronCore this node's device plugin advertises, so a second NeuronCore-bound process has nowhere to run. A 0.6B model's forward+backward over a handful of short sequences is cheap enough on CPU for a correctness smoke test -- confirmed on real hardware: each prompt's generate-plus-train step took about 3 seconds in the one successful run (generation itself `gen_time=0.2s`; the remainder is reward, forward, backward and the optimizer step together, not separately timed), small enough to prove the loop closes (see "What actually ran") without being a claim about production training cost |
| Weight update | Restart `sglang-neuron` pointed at a freshly-saved checkpoint, with `--dtype bfloat16` passed explicitly | The only officially-supported reload path (see above); no unofficial patch. `--dtype bfloat16` is explicit because `transformers.save_pretrained()` writes the checkpoint's `config.json` at the CPU training dtype (`float32`), which `sglang-neuron`'s default `--dtype auto` would read and refuse (see "What SGLang-Neuron is..." above) |

## What actually ran (this investigation's own evidence)

Six real-machine attempts across two sessions, each on a disposable cell built and torn down from scratch (`infra/foundation` + `gitops/` bootstrap). Teardown confidence each time: `terraform destroy` reported resources destroyed (83 in every session-1 attempt that reached `terraform apply`); a follow-up VPC lookup returned `InvalidVpcID.NotFound` (implying no instance, ENI or NAT remained in it); the remaining tag-based instance/volume/launch-template queries printed none. In session 2, `aws eks list-clusters` and `aws iam list-roles` (both account-wide by nature, filtered on this cell's own name/prefix) were additionally checked by hand before launching each subsequent attempt; the fullest sweep -- adding an unfiltered `aws ec2 describe-instances` enumeration of every running/pending instance account-wide and `aws identitystore list-groups` -- ran once, after the final (sixth) attempt. All of these found zero leftovers each time they ran.

**Session 1** (no code fix between attempts; real-machine budget exhausted at attempt 3):

| Attempt | Result |
|---|---|
| 1 | An orchestration mistake in this investigation's own verification script, not a platform or SGLang-Neuron issue: the gitops cell directory for the cell name used did not exist, so no capacity-pool/namespace was ever delivered and the run failed before requesting any Trainium capacity. |
| 2 | Pod stayed `Pending` with no node assigned for the full 15-minute wait. A read-only check immediately afterward found zero `trn2.3xlarge` instances running anywhere in the account at that moment; no Karpenter NodeClaim event was captured for this attempt specifically to confirm why. Consistent with a transient spot-capacity shortage in the one Availability Zone of `ap-southeast-4` that offers this instance type, but not confirmed as the sole cause. |
| 3 | A real node launched and the image pulled authenticated (a `trn2.3xlarge` spot instance; node allocatable `aws.amazon.com/neuron: "1"`, `aws.amazon.com/neuroncore: "4"`; image `public.ecr.aws/neuron/pytorch-inference-sglang-neuron:v0.1.0-...` pulled in 3m3.6s, 11.7 GB). The container started, ran for about 72 seconds, and exited with code 2 with no application-level log line captured: this attempt's own `kubectl logs -f` hit a client-side `context deadline exceeded` while the pod was still `ContainerCreating`, before the container ever started, and nothing re-attached it afterward. A `TaintManagerEviction` event appeared about 24 minutes after the container had already exited -- ordinary consolidation of the by-then-idle node, not the cause. `0.verify.sh`'s log-relaunch fix (below) and `train_grpo.py`'s server-log dump on failure were written here but not re-verified until session 2. |

**Session 2** (one real-machine attempt per fix, each attempt's own evidence informing the next fix; this session's 3-attempt / 3-Trainium-instance-hour budget used in full):

| Attempt | Result |
|---|---|
| 4 | The logging fixes from attempt 3 worked: `0.verify.sh`'s final non-follow `kubectl logs` capture, taken after the Job finished and before teardown, got the full application log this time. The server became healthy after 1001 seconds (compiling from cold -- no persistent compile-cache volume is mounted), then the first `generate_completions()` call failed with `HTTPError: 400 Client Error` from `/v1/completions` (container `exitCode=1`, an uncaught Python exception, not `sys.exit(2)`). Root-caused by reading `sgl-project/sglang-neuron`'s own source (commit `4e2432622bfab2c6663d12286a6813ef1a40bfe6`): `SGLANG_NEURON_SAMPLER` defaults to `"greedy"`, which refuses this script's `temperature=1.0` sampled request at admission. Fix: `job.yaml` now sets `SGLANG_NEURON_SAMPLER=topk_topp`. |
| 5 | The sampler fix worked: generation, reward and the first CPU training step all succeeded -- `STEP_SUMMARY step=0 mean_reward=12.8750 mean_loss=-8.4420`. Saving the step-0 checkpoint and restarting the server for step 1 then failed: `train_grpo.py` logged the *server subprocess's own* return code as `-9` (SIGKILL; `sgl-project/sglang-neuron`'s own scheduler process killing its process tree after hitting the error below, confirmed from the same dumped log, not an external OOM kill) -- a different number from the *container's* own exit code, which was `2` (`sys.exit(2)` on `train_grpo.py`'s own `wait_health()` returning `False`). `train_grpo.py`'s own server-log dump (added at attempt 3) captured the server's exact reason: `ValueError: Qwen3: the graphs compute in bfloat16, not torch.float32; launch with --dtype bfloat16`, raised by `sglang_neuron/models/transformer/config.py`'s `check_bf16_launch`. The checkpoint `transformers.save_pretrained()` wrote carries `config.json`'s `torch_dtype: float32` (the CPU training dtype), and `run_server.sh`'s default `--dtype auto` reads that and refuses it; the original Hugging Face checkpoint is already `bfloat16`, so only the post-training restart hit this. Fix: `start_server()` now passes `--dtype bfloat16` explicitly on every launch. |
| 6 | **Both fixes held. The loop closed.** Job status `Complete`. Server 1 healthy after 661s; step 0 (`generate_completions` ~0.2s/prompt, reward, train) produced `STEP_SUMMARY step=0 mean_reward=16.0000 mean_loss=-7.8760`; the checkpoint was saved, then the server was stopped and restarted against it with `--dtype bfloat16`, taking `restart_time=413.6s` (healthy after 411s -- `restart_time` is timed from after the checkpoint save, so it measures the stop/start/health-wait only, not the save itself); step 1 produced `STEP_SUMMARY step=1 mean_reward=13.8750 mean_loss=-4.2082`; the script printed `DONE generation->reward->train->weight-update(restart) loop ran 2 step(s) in 1090.5s total`. |

## On the two launch-configuration gaps this found

Both are things this script was not passing to `sgl-project/sglang-neuron` (commit `4e2432622bfab2c6663d12286a6813ef1a40bfe6`) that its own default resolution needed stated explicitly for this script's use case -- not bugs in `sglang-neuron` itself, and not bugs in this script's logic once each default was known. Neither has been filed to this platform's own upstream-findings issue yet (`AGENTS.md`'s stated convention for upstream gaps); that is still to be done as a follow-up, not claimed as done here.

1. **The device sampler refuses any non-greedy request unless `SGLANG_NEURON_SAMPLER` is set.** The default (`"greedy"`) is a reasonable choice for a plain inference server, but a GRPO-style loop needs sampled completions (`temperature=1.0`, `n>1`) to get a reward signal that varies across a group, so any caller of this plugin that wants RL-style sampling needs to know to set this explicitly -- it is launch configuration, not named per request, and not called out in the model-recipe docs this README already cites.
2. **A restart against a fine-tuned checkpoint needs `--dtype bfloat16` stated explicitly**, because the checkpoint's own `config.json` (written by whatever trained it) may not say `bfloat16` even though the compiled graphs require it. This is consistent with the documented "What is refused" list (a non-bfloat16 dtype is refused), but the *default* resolution path (`--dtype auto` reading the checkpoint) makes it easy to hit by surprise on a second (restarted) launch after training in a different dtype, as this script did.

## Prerequisites

| Requirement | Why |
| --- | --- |
| A cell built from `infra/foundation`, with `gitops/` bootstrapped | Kueue and the core add-ons, delivered to every cell |
| A `trn2.3xlarge` light-tier Trainium `NodePool` (`gitops/charts/capacity-pool`, `accelerator.methodLabel` = `distai.dev/neuron-method: device-plugin`) | This example's `nodeSelector`/toleration target it directly |
| A namespace this Job can run in (here, `distai-smoke`) -- the Job does not use Kueue admission | Where the Job and its ConfigMap/Secret are created |
| Internet egress from the Trainium node (the foundation's NAT gateway) | Pulling the 11.7 GB `sglang-neuron` image and downloading `Qwen/Qwen3-0.6B` from Hugging Face |
| `kubectl` and the AWS CLI on your workstation | Running the procedure below |

## Procedure (copy, paste, run)

```bash
export CLUSTER_NAME=your-cell-name
export AWS_REGION=your-region
export NAMESPACE=distai-smoke
cd examples/training/miles-trainium
aws eks update-kubeconfig --name "${CLUSTER_NAME}" --region "${AWS_REGION}"
ECR_PUBLIC_PASSWORD="$(aws ecr-public get-login-password --region us-east-1)"
kubectl create secret docker-registry ecr-public-pull -n "${NAMESPACE}" \
  --docker-server=public.ecr.aws --docker-username=AWS --docker-password="${ECR_PUBLIC_PASSWORD}" \
  --dry-run=client -o yaml | kubectl apply -f -
unset ECR_PUBLIC_PASSWORD
kubectl create configmap miles-trainium-script -n "${NAMESPACE}" \
  --from-file=train_grpo.py=./train_grpo.py --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f job.yaml
kubectl wait --for=condition=complete --timeout=60m job/miles-trainium-grpo -n "${NAMESPACE}" || true
kubectl logs job/miles-trainium-grpo -n "${NAMESPACE}"
```

`--for=condition=complete` only ever fires on success; this PR's own real-machine evidence (see "What actually ran") took about 18 minutes end to end (two server starts, one of them a restart, plus two short training steps), well inside the 60-minute default, but a retry against a cold compile cache could still run long. Lower `--timeout` if you would rather fail fast, or watch `kubectl get job ... -w` in another terminal instead.

This Job does not go through Kueue admission (it carries no `kueue.x-k8s.io/queue-name` label), so "namespace this Job can run in" above means only that -- a namespace, not a configured `LocalQueue`. `0.verify.sh` (below) is this investigation's own end-to-end verification: it also builds and tears down a disposable cell from scratch (which this simpler procedure assumes already exists), and itself needs a `gitops/cells/${NAME}/` directory with a trn2.3xlarge pool to exist on whatever revision it bootstraps -- this PR does not add a new one, so point it at an existing fixture or add your own first (`gitops/README.md` "Adding a cell").

## Known limits

- **No persistent compile-cache volume is mounted, and whether the second server start reused anything from the first is unconfirmed either way.** Neither session mounted a volume at the image's own compile-cache path (`CACHE_DIR=/cache` in `run_server.sh`); the first server start in the one successful run (attempt 6) was unambiguously cold (a freshly pulled image, no prior process). The second start (the restart, after training) ran inside the *same* container as the first, so its in-container `/cache` was not wiped between the two -- it took 411s, less than the first start's 661s, which is consistent with some cache reuse (same model architecture, same shapes) but is not confirmed either way without reading the compiler's own log, which this run did not capture. Mounting a persistent volume across the whole Job's lifetime would not change this specific comparison (the two starts already shared a filesystem); it would only help a *separate* Job run reusing a prior run's compiled artifacts, which was not tried.
- `trn2.3xlarge` for LLM serving is off-label per `sglang-neuron`'s own docs (see "What SGLang-Neuron is..." above) -- this example's own real-machine run is the first confirmation this investigation found that it actually serves Qwen3-0.6B there, but a future SDK/plugin release could still narrow or change what runs on this instance size without notice.
- The weight-update path is a full server restart, not a live reload -- the officially-supported method, not a workaround this example invented. Measured here: `restart_time=413.6s` (stop the old server, start the new one, wait for health; the checkpoint save itself happens before this timer starts, so it is not included). A separate, third-party public repository (`pengchenglu1997/trainium-sglang-rl`, read 2026-11-26) measured a comparable restart-based reload at about 455-460s for a similarly small model on larger Trainium hardware with a dedicated restart path; this result's own 413.6s is smaller, but the two numbers are not directly comparable (different hardware, different harness, and this run's two server starts shared a container, unlike a fresh process elsewhere), so treat the third-party figure as unrelated context, not a baseline this result beats or misses.
- Training runs on CPU, not on a NeuronCore -- correct for proving the loop closes at this model size, not representative of a production training step's cost or throughput, and not something this example claims to measure (see the Design table above for what was actually timed: about 3 seconds per prompt for generation plus training together, not training alone).
- `Qwen/Qwen3-0.6B` is downloaded by name, not pinned to a specific Hugging Face Hub revision -- a future upstream change to that model could change behavior without this example noticing.
- The reward function (a count of alphabetic words) is a free, deterministic placeholder chosen only so GRPO's group-relative advantage has something to normalize -- confirmed to produce varying rewards across samples (session 2's own completions ranged 8.0-20.0), not a meaningful training signal for any real task.
- `STEPS=2` and `GROUP_SIZE=4` are deliberately small (a correctness smoke test, not a benchmark); the loop closing at this size says nothing about whether it would still close, or how long it would take, at a larger step count, group size, or model.
- **Whether the restarted server actually served the step-0-updated weights, not the base checkpoint, is not directly confirmed.** What the evidence shows is that the restart pointed at the new checkpoint directory, the server became healthy, and generation then succeeded; no response field was checked to confirm which checkpoint the server actually loaded (a route such as SGLang's own `/get_model_info` might expose this, but whether `sglang-neuron` serves it was not checked). Separately: training runs in `float32`, and the dtype cast to `bfloat16` happens only when the checkpoint is saved for serving, which rounds each weight to roughly a `2^-8` relative step; two training steps at this script's learning rate (`1e-5`, AdamW) move most weights by less than that step, so this rounding alone could leave many weights at the same bfloat16 value as the base checkpoint even if training ran correctly. Neither point changes this example's own result (the loop closed, with the mean reward and loss both changing step to step), but both are outside what this evidence directly establishes.
- **`job.yaml`'s `pip install` runs inside the same Python environment `sglang-neuron`'s own server process uses**, so `transformers`/`requests`/`huggingface_hub` are installed or upgraded there rather than in an isolated environment; whether the pinned versions here match what the image already carries (and so whether this could change the server's own behavior, not only this script's) was not checked.
